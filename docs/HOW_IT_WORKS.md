# How PulsePredict works (and how to talk about it)

## 1. The one-sentence version
Raw cardiovascular data is cleaned and explored, three models are compared, the best full pipeline is saved, a FastAPI service validates requests and serves predictions from that exact pipeline, logs each one to SQLite, and a Streamlit dashboard calls the API.

## 2. Honest status of the data
The bundled CSV is **synthetic** (generated by `src/synthetic.py`) in the schema of the Kaggle cardiovascular dataset, with deliberate dirt injected (duplicates, BP typos, impossible heights/weights). It exists so the repo runs with zero downloads and contains no patient data. Say this up front in an interview; it is a strength (reproducible, privacy-safe), and swapping in the real CSV is one file copy + `python -m src.train`.

## 3. Walkthrough by stage

| Stage | File | What happens | Why it matters |
|---|---|---|---|
| Config | `src/config.py` | Paths, constants, column names in one place | No magic strings scattered around |
| Validate + clean | `src/data.py` | Checks schema; drops duplicates, impossible heights/weights/BPs, systolic ≤ diastolic; renames columns; age days → years; BMI | Each rule is counted and explained (`cleaning_report.json`). Plausibility limits, not percentile trimming |
| Preprocess | `src/preprocessing.py` | `Pipeline`: `FunctionTransformer(add_bmi)` → `ColumnTransformer` (StandardScaler on numerics, OneHotEncoder on cholesterol/glucose, passthrough binaries) → classifier | One object holds *all* steps → no train/serve skew |
| Train | `src/train.py` | Stratified 80/20 split **before** fitting; 5-fold CV ROC-AUC on train for 3 models; select; fit; save | Prevents leakage; test set untouched by selection |
| Evaluate | `src/evaluate.py` | Accuracy/precision/recall/F1/ROC-AUC, confusion matrix, ROC curves, permutation importance | Healthcare framing: FN vs FP |
| Inference | `src/predict.py` | Loads the joblib once (cached), builds a one-row DataFrame, `predict_proba`/`predict` | API stays thin |
| API | `api/schemas.py`, `api/main.py` | Pydantic validation (ranges, allowed codes, systolic > diastolic, no extra fields) → predict → log → respond | Bad input never reaches the model (422) |
| DB | `src/database.py` | SQLite `predictions(id, timestamp, prediction, probability, model_version)` + CHECK constraints; path overridable via `PULSEPREDICT_DB` | Privacy-conscious: outputs only |
| Dashboard | `dashboard/app.py` | 4 pages; prediction page POSTs JSON to the API | Demonstrates separation of UI and service |
| Tests / CI | `tests/`, `.github/workflows/tests.yml` | 24 tests; Actions runs pytest on push/PR | Reproducible quality gate |

## 4. Request lifecycle (`POST /predict`)
1. Streamlit sends JSON (`age`, `sex`, … `active`).
2. Pydantic `PredictionRequest` checks types, ranges, allowed category codes, and systolic > diastolic. Failure → HTTP 422, nothing logged.
3. `to_model_input()` renames `age` → `age_years`.
4. `predict_one()` builds a one-row DataFrame and calls the saved pipeline: BMI is added, numerics scaled with *training* means/stds, categories one-hot encoded, classifier predicts.
5. `risk_category`: probability ≥ 0.5 → "Higher-risk profile".
6. Result is logged to SQLite, then returned as JSON.

## 5. Demo script (the nine steps)
1. GitHub repo → README (architecture diagram, results, limitations).

8. GitHub → Actions tab → green tick.

## 6. Likely interview questions and answers

**Why a separate API instead of loading the model in Streamlit?** It separates UI from service logic: the API can be tested independently, reused by other clients, validated centrally, and is where logging lives. Streamlit becomes a thin client.

**What is data leakage and how did you avoid it?** Fitting scalers/encoders on all data lets test information influence training. I split first, and all transformers are inside a `Pipeline` fitted on the training split only. Cross-validation also refits the whole pipeline per fold.

**Why save the whole pipeline, not just the classifier?** Serving must apply identical preprocessing. Saving only the classifier would force me to re-implement scaling/BMI in the API and risk drift.

**Why not just pick the highest accuracy?** Accuracy ignores error type and threshold. ROC-AUC measures ranking quality across thresholds; recall and F1 reflect missed cases vs false alarms. In screening, false negatives are usually costlier. I chose by cross-validated ROC-AUC on training data so the test set stays an honest estimate.

**Your models score almost the same—so why Gradient Boosting?** Honestly, the differences are small (test AUC 0.819 / 0.821 / 0.823). Gradient Boosting had the best CV AUC, and Random Forest fell just outside my 0.001 tie tolerance. The tolerance is a judgement call. A logistic regression would be defensible when interpretability matters more.

**How did you decide what counts as an outlier?** From physiological plausibility, after looking at the distributions (values like 16020 mmHg are typing errors). I did not trim percentiles because that would delete real hypertensive patients. Every rule's removal count is reported.

**What does `probability` mean?** The model's predicted probability for class 1 given patterns in the training data. It is not calibrated against real outcomes and is not a personal chance of disease; the UI says so.

**Why is the data synthetic? Are your metrics real?** The metrics describe behaviour on the synthetic data (which I generated with a known nonlinear risk function). They demonstrate the engineering process, not clinical performance. With the real Kaggle file, you re-run `python -m src.train`; real-world AUC for that dataset is typically ~0.80, but I'd report whatever my run produces.

**Why does `weight` look important but BMI doesn't appear?** BMI is derived inside the pipeline; permutation importance shuffles *raw* inputs, so BMI's signal is split between height and weight.

**How would you improve it?** Calibrate probabilities; choose a threshold for a target recall; subgroup fairness analysis; SHAP; experiment tracking; Docker + deployment; drift monitoring on logged inputs.

**What do the tests cover?** Cleaning rules, BMI formula, pipeline probabilities in [0, 1], saved pipeline structure, SQL logging and constraints, and API behaviour: 200 / 422 cases, response fields, health, logging only on success.

**Known caveat:** the saved `.joblib` depends on the scikit-learn version (pinned to 1.8.0). If you see a load error, run `python -m src.train` to regenerate it.
